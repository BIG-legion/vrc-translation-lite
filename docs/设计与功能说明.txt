VRC Translation Lite——设计与功能说明
======================================

作者：little-legion

一、设计想法
------------

VRCT 已经能够完成麦克风与扬声器语音识别、翻译和 VRChat OSC 输出，但不同模型服务的接口格式、令牌配置和启动方式并不统一。普通用户往往需要同时打开多个程序、记住多个端口，并手动修改 VRCT 配置。

本项目的想法是把这些步骤收拢成三层：

1. VRCT 负责语音识别、界面显示和 VRChat 输出。
2. 兼容中转负责把 VRCT 的 LM Studio / OpenAI 格式请求转换成稳定、严格的翻译请求。
3. New API 负责管理模型渠道、令牌、模型别名和在线或本地上游。

图形安装器负责建立连接，图形启动器负责管理生命周期。用户只需要记住一个入口：“VRC 翻译启动器”。

二、组件职责
------------

图形安装器：

- 选择 VRCT 与 New API 可执行文件。
- 设置安装目录。
- 写入最多三个模型名称。
- 写入 New API 令牌或允许稍后配置。
- 复制启动器、中转和运行时。
- 备份并配置 VRCT config.json。
- 创建开始菜单与桌面快捷方式。

图形启动器：

- 检查 New API、中转和 VRCT 的运行状态。
- 按顺序启动三个组件。
- 将后台组件以隐藏窗口方式运行。
- 打开 New API 管理页面和令牌配置页面。
- 只结束本次由启动器启动的后台进程。
- 监控 VRCT，退出游戏翻译流程后自动清理后台服务。

兼容中转：

- 提供 OpenAI 兼容的模型列表与聊天补全接口。
- 将请求转发到本机 New API。
- 合并 VRCT 发送的短上下文片段。
- 对连续增量片段去重，避免一句话被重复加入历史。
- 固定 temperature=0。
- 将原文包裹在明确的数据边界中。
- 强制模型只返回译文。
- 结合上下文进行高置信度语音识别纠错。
- 阻止上下文中的指令改变翻译任务。

三、上下文策略
--------------

语音识别经常把一整句话拆成三四次增量发送。如果简单保留最近三条记录，实际可能只覆盖同一句话的一小部分。因此中转采用最多 15 条短上下文，并同时限制：

- 单条最多 400 个字符。
- 总上下文最多 5000 个字符。
- 连续增量片段会尝试替换旧片段，而不是全部重复追加。
- 完全重复的内容不会再次加入。

上下文只用于判断代词、语气、敬语、俚语、话题和高置信度识别错误。当前待翻译原文始终拥有最高优先级。

四、严格翻译策略
----------------

模型被定义为确定性翻译引擎，而不是聊天助手。规则包括：

1. 每个输入都必须翻译，包括问题、命令、拒绝语和“不要翻译”之类的句子。
2. 不回答原文中的问题。
3. 不添加解释、前缀、引号、注释或多余标点。
4. 只输出一种目标语言的译文。
5. 温度固定为 0，减少措辞随机变化。
6. 只修正结合上下文能够高置信度判断的语音识别错误，不随意改写含义。

五、模型与渠道设计
------------------

安装器允许填写最多三个 New API 模型或模型别名。推荐把它们设计为：

- 快速模型：低延迟，适合连续对话。
- 均衡模型：日常交流的默认选择。
- 高质量模型：复杂长句、敬语或含糊语境。

模型可以来自在线 API，也可以是经 New API 转发的本地 OpenAI 兼容服务。VRCT 只连接固定的中转地址，因此切换模型时无需改变网络结构。

六、语音识别与翻译的边界
------------------------

Whisper 或 Google 语音识别属于 VRCT 层。中转无法恢复识别阶段完全丢失的声音，但可以利用上下文修正明显的同音字、词边界、重复片段和标点问题。

其他玩家语音的准确度主要受以下因素影响：

- 扬声器捕获设备是否正确。
- 玩家语音与世界背景音乐的音量比例。
- 目标识别语言。
- 静音结束时间、转录间隔和最小单词数。
- Whisper 模型大小与 CPU/GPU 性能。

七、使用场景
------------

- 中文语音实时翻译成英语或日语并发送到 VRChat 聊天框。
- 接收英语或日语玩家语音，在 VRCT 界面或 VR Overlay 中显示中文。
- 同一套 New API 中切换不同翻译模型。
- 通过本地模型降低 API 依赖。
- 在 VR 模式中用 OSC 和 Overlay 完成双向交流辅助。
